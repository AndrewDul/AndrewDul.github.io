01 / ARTIFICIAL INTELLIGENCE & ROBOTICS

NeXa

From a local AI desktop assistant to a physical robot — and towards a device-independent, user-owned AI system.

An ongoing, iterative engineering project. The repositories below represent different phases and purposes, not three separate finished products.

Context

I wanted to understand what it takes to make AI useful beyond a chat window: speech recognition, responsive feedback, local models, cameras, hardware and eventually a mobile robot. This became a practical exercise in integrating software with real devices.

Engineering approach

I broke the system into smaller, testable stages: audio capture and speech recognition; intent normalisation and routing; model-backed answers or deterministic commands; speech output; and visible status updates. For robotics, hardware readiness and safe movement decisions sit alongside those stages rather than being treated as ordinary chatbot responses.

ENGINEERING DECISIONS

Problems I investigated and what I changed

Responsive voice interaction

Speech is a chain of capture, recognition, routing, response generation and playback. Delays and uncertain transcripts made the experience feel unreliable. I separated fast deterministic commands from model-backed answers, improved state feedback and used focused checks to isolate bottlenecks.

Models on constrained hardware

On a Raspberry Pi, model size, responsiveness and capability compete. Rather than send every request to a large model, I explored smaller local speech components and task-specific routing, with clear fallback paths and explicit device limitations.

Unreliable cameras and sensors

Physical inputs can be missing, stale or inaccurate. The design distinguishes device availability from usable data, with camera and sensor validation before a downstream decision. The public RoVe examples make those safety checks easier to inspect.

Safe robot behaviour

A movement request must never be treated as an ordinary generated sentence. The robot experiments use conservative choices — stop, wait, require a valid state or move slowly — while keeping movement behind explicit checks.

AI speaking over itself

In the newer architecture, a documented live regression showed local voice activity detection triggering on NeXa's own playback. The team of software components needed clearer interruption, playback and audio-reference boundaries. The latest documented investigation had not yet passed its full hardware acceptance criteria.

Keeping the code understandable

As the system grew, one fault could appear to originate in another module. I moved towards explicit responsibilities, smaller changes, regression tests, smoke tests, decision records and milestone reports rather than relying on a large monolithic assistant script.

ARCHITECTURE & CODE

What happens when someone speaks to NeXa?

  1. Capture — the microphone provides audio to the speech pipeline.
  2. Recognise — Vosk or a Whisper-based path turns audio into candidate text, depending on the implementation and configuration.
  3. Understand and route — normalise the request; distinguish deterministic commands from requests that need a language model.
  4. Check capabilities — determine whether the required device or safe action is available.
  5. Respond and display — generate text or a controlled action, produce speech where enabled, and update the Visual Shell.
  6. Verify — use tests, runtime diagnostics and hardware smoke checks to detect regressions.

This is a conceptual summary across the project's iterations, not a claim that all three repositories run the same pipeline or that all planned modules are complete.
