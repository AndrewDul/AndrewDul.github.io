## NeXa ecosystem

NeXa is a long-running local-first AI and robotics programme rather than one finished consumer application. The earlier Smart Desk AI Assistant is a Python and Raspberry Pi runtime; its public documentation describes audio capture, VAD, bilingual Vosk command recognition, Faster-Whisper fallback, deterministic routing, Piper TTS, a Godot Visual Shell, camera/pan-tilt paths, guarded mobile-base controls and local memory. A deliberate design is that high-confidence, safe commands do not require an LLM.

NeXa RoVe is the public physical-platform and engineering-tour repository. It documents a Raspberry Pi 5 platform, displays, microphone, cameras, sensors, mobile base, diagrams, simplified runnable examples, photographs and testing notes. Its runtime model separates input, understanding, decision, feedback and optional hardware actions. Uncertain state must lead to conservative outcomes such as wait or stop.

The newer `NeXa` repository is the canonical architecture track. Its documented principles are local-first, privacy-first, user-owned data, provider and device independence, a single clear authority per responsibility, replaceable transport and model boundaries, separation of history from long-term memory, and no hidden fallback response paths. Reports explicitly distinguish shipped work, research, plans and unresolved questions.

**Why the architecture changed.** The newer project did not blindly carry forward the older multi-agent runtime. Its ADRs record evidence that a legacy setup had a very large central entry point, roughly fifty agent packages, latency and failure-path complexity, and canned/late grounding problems. The redesign keeps the useful lessons but rejects duplicated brains and silent fallback answers. The accepted text path is deliberately small: UI or later speech-to-text → one `ConversationSession` → bounded provider context → `ModelProvider` stream → append completed assistant message. Providers are adapters, never the owner of identity, history or policy. A provider failure must fail closed honestly instead of silently changing model or answer path.

**Measured local-AI decisions.** The documentation records Raspberry Pi 5 benchmark evidence rather than a generic claim that local models are fast. CPU was the viable LLM route; V3D/Vulkan was not production-ready and the Hailo route had model/context/toolchain limits. A first Qwen baseline was compared with Bielik and later Gemma alternatives. The reported trade-off: 4B-class quality was not dramatically slower than 3B on this hardware, but it was still marginal for natural conversation, so streaming, bounded context, concise persona design and provider swapping were architectural concerns. Later evaluation found Gemma 4 variants stronger for bilingual naturalness, but the exact baseline was changed only through evidence and an ADR rather than hard-coding a vendor into core logic.

**Voice and safety evidence.** Public RoVe examples deliberately use mocked inputs and standard-library tests: voice activity, commands, sensor snapshots, detections and safe follow/movement decisions. The private/newer documentation goes further: local realtime voice is described as a frozen baseline with Pipecat local transport, Silero VAD, whisper.cpp, bilingual language guard, `ConversationSession`, local model, speech planning, Piper output, hardware AEC and deliberate interruption semantics. A cloud voice experiment was treated as a replaceable provider feasibility test, not a new system brain. Documentation records real hardware sessions, explicit performance observations, provider/reconnect risks and a rule that derived context may leave the device only under defined privacy/policy boundaries. Any answer must distinguish an operator-confirmed experiment or documented architecture from a broadly released capability.

## Warehouse Barcode Studio

A React, TypeScript and Vite local-first browser application for creating printable labels. It supports Code 128, Code 39, Code 93 and QR formats; validates values by format; treats each non-empty text line as a label; imports Excel, Word, Markdown and text; maintains a label queue and active preview; exports PNG, SVG, PDFs and ZIP packs; and invokes the browser print dialog with Zebra ZD220, warehouse, shelf-edge, small-item and custom profiles. Values stay on-device: the application does not send label values to an API, save them in local storage or log them. The project uses Vitest tests for parsing and validation, TypeScript checking and a production build.

**Problem, choices and evolution.** The product problem was converting operational identifiers into printable labels without asking a warehouse user to upload potentially sensitive identifiers to a service. The solution was intentionally static: import, parsing, validation, rendering and export happen in browser memory, while output files are created only on an explicit export. Format-specific validation prevents an apparently generated label from silently representing an invalid value. Excel input is processed across sheets in workbook order, while Word/text are line-oriented and Markdown has minimal presentation markup stripped. The implementation relies on purpose-specific client libraries: JsBarcode for linear codes, `qrcode` for QR, SheetJS for spreadsheets, Mammoth for Word, jsPDF for PDF and JSZip for packs. Heavy import/export code is lazy-loaded to reduce the initial download. A real hosting issue was documented: GitHub Actions was blocked by the account's billing state, so the project retained CI configuration but added a verified `docs/` static Pages fallback rather than pretending CI deployment had succeeded. A later scan mode introduced a searchable one-label view, bounded queue scrolling, office-sheet layouts and the guard that clears search before printing so printing never accidentally exports only filtered results.

## KoffeeCraft

A Kotlin Android coffee-shop application with XML views, fragments, Navigation Component, Room and SQLite. It separates customer and administrator workflows. Customer work includes account access, browsing and customising products, cart and checkout, saved payment methods, order history/status, favourites, rewards, notifications and feedback. The admin area uses its own activity and navigation graph for dashboard, menu, orders, feedback and settings. Technical decisions include PBKDF2WithHmacSHA256 plus a per-user salt for password storage; Room entities/DAOs/repositories for local persistence; a distinct order lifecycle from PLACED through PREPARING, READY and COLLECTED; one feedback record per order; soft product disablement for availability versus hard deletion; and local UI filtering when the existing Room stream is adequate. The repository includes unit tests for validation, payments and rewards, plus instrumented tests for customer/admin flows, repositories and DAOs.

**Problem-solving evidence.** The documentation records actual failures and their fixes. AndroidX dependency metadata required a newer API level, so compile/target SDK were updated to 36; adaptive icons required a compatible minimum SDK, so `minSdk` was set to 26. Database Inspector initially showed no data because the Room database was not yet created, solved by invoking a simple DAO operation during development. Android 13+ notifications required both manifest permission and runtime `POST_NOTIFICATIONS` consent. An order screen originally re-ran status simulation when a historic order was opened; navigation now passes `simulate=true` only from a fresh checkout, and the first Flow emission is not treated as a state change. The status simulator was moved outside Fragment lifecycle into an `OrderSimulationManager` so it continues when a user leaves the screen. A Room mismatch between Kotlin `isActive` and stored `isAvailable` caused KSP failures, crashes and disappearing products; property mapping, queries and migration were aligned and an add-column-if-missing migration was used. Feedback was redesigned from order-level to `orderItemId` level because an order can contain several products; this enables accurate product analytics and multiple product reviews. Tests record 48 unit tests for validation/payment/rewards/admin validation, repository and DAO instrumented coverage, and Espresso smoke coverage for customer and administrator flows.

## LifeOS

A local-first personal life operating system built with Tauri 2, React, TypeScript and Rust. The public repository contains product, architecture, research-decision and project-state documentation. Its reports show a staged approach to UI, storage, goals, projects, tasks, milestones, audit safety and personal-knowledge features. It is an active engineering project, so the assistant must describe documented status rather than present planned capabilities as released.

**Current verified maturity and safeguards.** LifeOS is Windows-first, designed to become cross-platform. Its implemented M2 scope includes Goals, Projects, GoalRelations, Milestones, Tasks, and the full v0.1 Memory and Relation mutation families; calendar, recurring rules, retrieval/context packs and most AI product features remain incomplete or architecture-only. SQLite foreign-key integrity, atomic operations, typed errors and mandatory audit snapshots are design priorities. Storage hardening addresses a real key-lifecycle risk: an existing database missing its credential must fail safely rather than generate a replacement key. Personal knowledge distinguishes facts, relations, episodes, sources and evidence; it also models sensitivity, confidence and epistemic state. The hard-delete flows are intentionally strict: `ForgetMemory` and `ForgetRelation` require confirmation, have no undo, remove target data and associated evidence safely, scrub relevant audit snapshots and protect the SELF identity. At the reported point, the repository recorded 543 passing tests for the completed relation family. No Tauri command had yet wired the Memory actions into the running interface, so the assistant must not claim that a user can already operate them from the app.
